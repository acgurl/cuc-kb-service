## 4. 线上延迟（Phoenix 实测，24 块真实候选）

块数：8/12/16/24 块的 P50 为 1.30/1.45/1.19/1.46 s，P90 和最大值都由网络长尾决定（每档都出现约 16 s 的请求）。

连接方式（各 40 次，交错执行，请求间随机空闲 0～3 s）：

| 方式 | P50 | P90 | P95 | 最大 | >4 s（线上会超时降级） |
|---|---:|---:|---:|---:|---:|
| 现状：每次新建 TCP+TLS（`urllib.urlopen`） | 1.58 | 21.08 | 21.90 | 22.23 | 4/40 |
| 长连接复用（`http.client` keep-alive） | **0.87** | **1.49** | 2.03 | 2.68 | 0 |
| 对冲请求（2 s 未返回再发一份，取先到） | 1.33 | 2.81 | 2.97 | 3.37 | 0 |

TCP 建连 RTT 约 0.18 s。长尾出在建连 / TLS 握手阶段，长连接直接绕开；现状下约 10% 的请求会超过 4 s 超时，退化成不 rerank 的结果，所以线上实际质量低于离线评测。

空闲连接存活：同一连接空闲 15/45/90/180/300 s 后再发小请求，全部复用成功（0.27～0.53 s），服务端没有回 `Connection: close` 或 `Keep-Alive` 超时头。线上流量稀疏时长连接也能保持住。

## 5. 建议（按收益排序）

1. **CloudReranker 改为长连接**（P0）：`search_core.CloudReranker._post` 从 `urllib.urlopen` 改成按线程复用的 `http.client.HTTPSConnection`（`/v1/search` 是同步路由，跑在线程池里），连接失效时重建并重试一次。预计 P50 1.5 s → 约 0.9 s，消除约 10% 的超时降级。可再叠加对冲请求（建连后仍 >2 s 才发第二份）兜底，但会多花 token，先不做。
2. **删除精排后的三组加分**：零影响的死规则，删掉后调参面更小。保留通用汇编降权和覆盖度加分。
3. **扩无答案集到 ≥50 题并重新标定阈值**：当前两类分数在 0.71～0.72 交叠，0.75 只靠 20 道题支撑。
4. **单词查询在 agent 层改写**（如「国奖」→「本科生国家奖学金评选」），不改检索阈值。
5. 候选规模保持 24；只有要省 token 时再切 16（质量持平）。

## 6. 上线结果（2026-11-01）

已上线建议 1 和 2：`CloudReranker._post` 改成每个线程一条 keep-alive 连接（`http.client`）。复用的连接断开时重建并重试一次；超时直接抛出，不重试，交给调用方降级为不 rerank 的结果。同时删除了 `INTENT_PHRASES` / `DEFINITION_HINTS` / `DURATION_HINTS` 加分和 `KB_PHRASE_BONUS` / `KB_TITLE_PHRASE_BONUS`；`_adjusted_rerank_score` 只保留通用汇编降权。离线复跑和改动前逐项一致。
