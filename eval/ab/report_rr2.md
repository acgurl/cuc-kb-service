## 拒答：纯阈值 vs 管线

| | heldout 保留有答案题 | heldout 正确拒答 | v5 保留 | v5 拒答 |
|---|---:|---:|---:|---:|
| 纯阈值 best_rerank ≥ 0.75（always） | **86/87** | **10/10** | 116/117 | 10/10 |
| v5 标定阈值 0.7538 | 86/87 | 10/10 | 116/117 | 10/10 |
| 线上管线 `_judge_answer`（always） | 85/87 | 8/10 | 115/117 | 10/10 |

管线比纯阈值多出的 4 个错误，都来自属性可答性规则（`ATTRIBUTE_HINTS` / `SPAN_PATTERNS` / `STRICT_ATTRIBUTES`）的改判：

- **误答**：hn03「毕业典礼的学位服在哪里租？」rerank 0.363；hn07「校内打印店几点关门？」rerank 0.543。两条 rerank 分都低于阈值，本应拒答，但规则在召回文档里找到了地点/时间类片段，就把 `no_answer` 改成了 False。
- **误拒**：h02「拿政府奖学金的留学生本科生想转去别的学校可以吗？」rerank 0.935；h67「学校的收费项目没公示能收钱吗？」rerank 0.859。两条都高于阈值，但属于 strict 属性，规则没在 Top5 里找到对应片段，就强制拒答了。

也就是说，换成 qwen3-rerank 后，单靠 rerank 阈值就足以做拒答判断，属性规则从帮忙变成了拖后腿。这个结论只在 20 道无答案题上验证过，还需要更大的无答案集复核。

## 线上可行性（Phoenix 美西 → 百炼北京）

- 24 个真实候选块（约 4.4k token），IPv4 和 IPv6 各 10 次，20/20 成功，单次 0.86～2.32 s。另有一次 3 文档的小请求出现过 22.8 s 的长尾。
- 线上现有 `RERANK_API_TIMEOUT=4`，超时会回退到本地 CPU 模型（Phoenix 上 17～19 s）。必须改为超时后直接使用不 rerank 的结果，否则长尾会被放大。
- 费用：约 4.4k token/查询。

## 建议上线方案

1. reranker 换成百炼 `qwen3-rerank`，每条都 rerank（去掉 `INTENT_RERANK_HINTS` 等条件触发规则），阈值保持 0.75。
2. 拒答只用 rerank 阈值，停用属性可答性改判。可以保留成"只加不减"的提示字段，但不再改写 `no_answer`。
3. 云端失败或超时时，降级为不 rerank 的结果，不再回退到本地 CPU 模型。保留本地回退时，必须加 sigmoid 修复尺度 bug。
4. 嵌入维持 bge-small-zh，Qdrant 不需要重建。
5. 上线后用 `eval/heldout` 和 v5 通过线上 API 复测一次，确认与离线结果一致。
